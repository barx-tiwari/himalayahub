# HimalayaHub v5 — upgrade guide

This release removes gold prices and adds: an anonymous community, Hidden Gems of Eastern Nepal,
a Travel Nepal Guide for foreign visitors, verified stays + Google Places, sign-up, Sign in with Apple,
guest mode, token auth for future mobile apps, saved trips/favourites, and screenshot deterrence.

Contents: 1 Migration · 2 Environment variables · 3 Authentication setup · 4 Google services ·
5 API reference · 6 Community & moderation · 7 Screenshot deterrence · 8 Content accuracy ·
9 Deployment notes · 10 Not in this release

## 1. Migration (from v4)

```bash
npm install
npm run db:generate
npm run db:deploy          # applies prisma/migrations/20260925000000_v5_community_stays_auth
npm run db:seed            # adds the 6 communities and the 10 Hidden Gems (never deletes anything)
npm test
```

What the migration does:

| Change | Detail |
|---|---|
| Removed | `GoldPrice` table; `MarketSnapshot` rows with `GOLD`/`SILVER`; the `GOLD` `ApiSetting` row |
| Added tables | `RefreshToken`, `Stay`, `SavedTrip`, `Community`, `CommunityPost`, `CommunityComment`, `CommunityVote`, `ContentReport`, `CommunityBan` |
| Added columns | `UserProfile.travelInterests`, `travelerType`; `Destination.region`, `elevationM`, `difficulty`, `distanceFromKtmKm`, `isHiddenGem`, `hiddenGemRank`, `guide` (JSON) |

Everything except the gold removal is additive. **Back up first** (`npm run db:backup -w @himalayahub/api`).
The migration SQL was applied end-to-end (init + v5) against SQLite during development.

Old `/gold` links redirect to `/markets`. You can delete `GOLDAPI_KEY` and `NEPAL_GOLD_JSON_URL` from your `.env`.

## 2. Environment variables (new in v5)

All server-side; none reach the browser. Existing variables are unchanged (see `.env.example`).

| Variable | Required | Purpose |
|---|---|---|
| `APPLE_CLIENT_ID` | for Apple sign-in | Your **Services ID** (e.g. `com.himalayahub.web`), not the App ID |
| `APPLE_TEAM_ID` | for Apple sign-in | 10-character team id |
| `APPLE_KEY_ID` | for Apple sign-in | Key id of the Sign in with Apple key |
| `APPLE_PRIVATE_KEY` | for Apple sign-in | Contents of the `.p8` file. One line with `\n` is fine |
| `JWT_SECRET` | optional | Signs mobile access tokens. Defaults to a key derived from `SESSION_SECRET` |
| `JWT_ACCESS_TTL_MIN` | optional | Access-token life, default 15 |
| `REFRESH_TTL_DAYS` | optional | Refresh-token life, default 60 |
| `COMMUNITY_ALIAS_SECRET` | optional | Keys the anonymous aliases. Defaults to a derived key. Changing it only changes *new* aliases |
| `GOOGLE_MAPS_API_KEY` | optional | Server key for the Places proxy (nearby stays, ratings, reviews) |

Rotating `SESSION_SECRET` signs everyone out and, if `JWT_SECRET`/`COMMUNITY_ALIAS_SECRET` aren't set,
also changes the derived keys. Set those two explicitly in production so you can rotate independently.

## 2b. Email delivery (required for sign-up codes)

Sign-up now sends a **6-digit code** (valid 10 minutes, 5 tries, resend after 60 s, max 5 per hour) plus a
fallback link. In development the email prints in the API console. To send real emails, pick one:

| Option | Variables |
|---|---|
| Resend (resend.com, free tier) | `MAIL_PROVIDER=resend`, `MAIL_API_KEY=re_…`, `MAIL_FROM="HimalayaHub <no-reply@your-domain>"` (verify the domain in Resend) |
| Brevo (brevo.com, free tier) | `MAIL_PROVIDER=brevo`, `MAIL_API_KEY=xkeysib-…`, `MAIL_FROM` = a sender verified in Brevo |
| Any SMTP (e.g. Gmail app password) | `SMTP_URL=smtps://user:app-password@smtp.gmail.com:465` and `npm i nodemailer -w @himalayahub/api` |

Set `MAIL_SEND_IN_DEV=true` to send real emails while developing. SMS codes are not included (they cost per
message); an SMS provider such as Sparrow SMS could be added to the same `sendVerification` function.

## 3. Authentication setup

**How it fits together.** The website keeps httpOnly session cookies (they can't be stolen by page
scripts — safer than JWTs in the browser). Mobile apps use short-lived JWT access tokens plus rotating
refresh tokens. Both paths share the same accounts, lockout rules and roles.

**Roles.** Product names map onto the existing database roles:

| Product role | Who | Can |
|---|---|---|
| Visitor | signed out, or "Continue as guest" | read everything, including the community |
| Verified user | `USER`/`STUDENT` with a confirmed email | post, comment, vote, report, save places and trips |
| Moderator | `MODERATOR` (and `EDITOR`) | moderation queue (`comments.moderate`) |
| Admin | `ADMIN`, `SUPER_ADMIN` | everything above + admin areas |

**Email/password.** Sign-up now exists on `/login` ("Create an account"). New accounts get a confirmation
email (in development the link prints to the API console). Posting needs the confirmed email.

**Google** (unchanged, already supported). In Google Cloud → APIs & Services → Credentials, create an
OAuth client (Web). Authorised redirect URI: `${API_URL}/api/auth/google/callback`. Set
`GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`. The button appears automatically.

**Apple.**
1. Apple Developer → Identifiers: create an App ID with "Sign in with Apple", then a **Services ID**.
2. Configure the Services ID: domain = your API domain; return URL = `${API_URL}/api/auth/apple/callback`.
   Apple requires **HTTPS and a real domain** — it will not accept `localhost`. Test on a staging domain.
3. Keys → create a key with Sign in with Apple; download the `.p8` once.
4. Set the four `APPLE_*` variables. The button appears automatically.

Apple posts the result back cross-site, so the callback uses a `SameSite=None; Secure` state cookie and
is protected by state + nonce checks. Apple only sends the user's name on their first sign-in, and may
give a private relay email — that is expected.

**Mobile apps (token auth).**
```
POST /api/auth/token          { email, password, deviceName? } → { accessToken, refreshToken, expiresIn, user }
POST /api/auth/token/refresh  { refreshToken }                 → new pair (old refresh token dies)
POST /api/auth/token/revoke   { refreshToken }                 → signs that device out
Authorization: Bearer <accessToken>   on every other request
```
Store the refresh token in the Keychain / Android Keystore. Presenting an already-used refresh token
revokes that device's whole token family (theft detection). Password changes revoke all tokens.

## 4. Google services

**Maps on destination pages** use OpenStreetMap embeds (no key) plus "Directions in Google Maps" links
(no key). **Google Places** (optional) powers "Show nearby places from Google" on Hidden Gem pages:

1. Google Cloud → enable **Places API (New)**.
2. Create an API key. Restrict it to the Places API, and (if your API has a fixed outbound IP) to that IP.
3. Set `GOOGLE_MAPS_API_KEY`. Set a **daily quota and a billing budget alert** — the proxy rate-limits
   each visitor to 20 requests/minute, but Google bills per request.

Terms-of-service choices built in: Google results are never stored or cached by us (only a `place_id`
may be saved on a verified stay); they're labelled "unverified" and attributed to Google; ratings and
reviews only ever come live from Google.

**Stays.** Editors add verified hotels/homestays via `POST /api/admin/stays` (permission `stays.manage`).
A listing only appears publicly when `isVerified` is true **and** a verification note says how it was
checked (e.g. "phoned owner 2026-10-02"). We never generate hotel names, phone numbers or ratings.
*(An admin screen for stays is not built yet — use the API or Prisma Studio for now.)*

## 6. Community & moderation

- **Anonymity.** Members appear as aliases like `Misty-Danfe-4821`: the same inside one community,
  different in every other, derived with a keyed hash so they can't be reversed to an account.
  Public responses never include user ids, names or emails.
- **Moderators are also kept blind.** The queue shows alias + an opaque "author key" (same key =
  same person) so repeat abuse is visible without revealing identity. Bans target a post/comment and the
  server resolves the author. Every action is audit-logged.
- **Be honest with users about the limits.** The platform itself *can* link posts to accounts (it has to,
  to act on abuse and legal requests). The Privacy page should say so.
- **Spam checks** score each post (links from new accounts, promo phrases, flooding, duplicates, shouting,
  phone numbers/emails). Score ≥ 0.6 → held for review instead of published. Three separate reports hide an
  item until reviewed. Self-voting is blocked.

## 7. Screenshot deterrence

> **No platform can guarantee complete screenshot prevention. These measures only discourage capture.**

On community pages (web): right-click menu disabled inside the content; a faint tiled watermark with the
date; content blurs when the tab is hidden or the window loses focus; on the PrintScreen key (where the
browser reports it) content is briefly hidden and the clipboard overwritten; printing is blocked via CSS.
None of this stops OS shortcuts (Win+Shift+S, Cmd+Shift+4), screen recorders, dev tools or a phone camera.

Mobile (for when native apps exist — there is no mobile app in this repo yet):
- Android: `window.setFlags(WindowManager.LayoutParams.FLAG_SECURE, WindowManager.LayoutParams.FLAG_SECURE)`
  on community screens blocks screenshots and recording on most devices.
- iOS has no equivalent block. You can detect `UIApplication.userDidTakeScreenshotNotification` after the fact
  and hide content while `UIScreen.main.isCaptured` is true (recording/mirroring).

## 8. Content accuracy (Hidden Gems)

Content lives in `apps/web/src/data/hiddenGems.js` (offline fallback) and is seeded into the database, where
editors can refine it in the CMS. Elevations, distances, map pins and costs are **approximate** and every
page says so until an editor sets `guide.verifiedAt`.

**Needs local research:** Loden Village and Rauta Pokhari (pages ask visitors for help).
**No photos are bundled** — add verified, credited photos through the destination gallery in the CMS.
Permit rules (restricted areas, the 2023 licensed-guide requirement) should be re-checked against the
Department of Immigration and Nepal Tourism Board before each season.

## 9. Deployment notes

Unchanged from v4 (see README), plus:
- Apple sign-in needs HTTPS on `API_URL`.
- If the API is on a different origin than the site, keep `APP_URL`/`CORS_ORIGINS` correct. The CORS
  allow-list now includes the `Authorization`, `X-Filename` and `X-Alt` headers.
- Moderators need `MODERATOR` role — set it in Prisma Studio until the Users admin screen ships.
